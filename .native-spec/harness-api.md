## Conventions used throughout

- Error envelope (default): `{"error": {"code": string, "message": string}}` via `writeError`.
- Scope-failure envelope (403): `{"error": "insufficient_scope", "required": string}` via `writeScopeError` — note this is a *different shape* (string, not object) from the default error envelope.
- 405s set an `Allow` header and use the default error envelope with code `method_not_allowed`.
- One exception to the default error envelope: `POST /v1/config/reload` failure returns `{"error": string}` (bespoke, not `{"error":{...}}`).
- All list endpoints normalize `nil` slices to `[]T{}` before marshaling (arrays are never JSON `null`).
- Scopes: `runs:read`, `runs:write`, `admin` (`internal/store/apikeys.go`). `admin` satisfies any check; `runs:write` satisfies `runs:read`. When no API-key store is configured, or `AuthDisabled`, all scope checks pass through.
- Tenant isolation: when auth is enabled, cross-tenant access to a run/conversation/checkpoint returns **404** (not 403) — the existence of another tenant's resource is never revealed. `tenant_id` supplied in a request body/query is validated against the authenticated key's tenant (mismatch → 400); an empty value is silently filled from the auth context.

## 1. Auth

- **Mechanism**: `Authorization: Bearer <token>` header only. A legacy `?token=` query-param fallback was deliberately removed (secrets-in-URLs hardening) — there is no browser/EventSource-only auth path in this codebase.
- **Validation**: `authMiddleware` (`internal/server/auth.go`) calls `s.runStore.ValidateAPIKey(ctx, rawToken)`. Errors: no store configured → auth implicitly disabled; expired key → 401; unknown key → 401; internal error → 500 (message not leaked).
- **Disabling auth**: `ServerOptions.AuthDisabled = true`, or environment variable `HARNESS_AUTH_DISABLED=true`. When disabled (or no store), every scope check passes and `tenant_id` is taken from the request as-is.
- **Context injected per request**: tenant ID, first-8-chars API key prefix (audit trail), and validated scopes (`[]string`).
- **Key provisioning**: there is **no HTTP route to create/list/revoke API keys**. Keys are `store.APIKey` rows created via the Go `store.CreateAPIKey` / `store.GenerateAPIKey` API only, operating directly against the store backing harnessd (SQLite or in-memory). `harnesscli auth login` (`cmd/harnesscli/auth.go`) generates a raw token client-side with `store.GenerateAPIKey(tenant, name, [runs:read, runs:write, admin])` and writes it to `~/.harness/config.json` (`{"server":..., "api_key":...}`) — **it does not call any harnessd endpoint or insert the key into a store**, so this only produces a token harnessd will accept if that same key row is independently persisted into the store harnessd reads (e.g. same-process/same-DB deployment), or if auth is disabled. There is no verified remote key-provisioning flow.
- Provider (LLM) API keys are a separate concept — see `PUT /v1/providers/{name}/key` in the route table; that is not the harnessd auth key.
- Webhook/trigger routes (`/v1/external/trigger`, `/v1/webhooks/{github,slack,linear}`) **bypass Bearer auth entirely** and instead validate a per-source HMAC signature (see their table rows).

## 2. Launching / configuring harnessd

Binary: `cmd/harnessd`. Modes:
- HTTP server (default): `harnessd [--profile <name>]`.
- MCP stdio mode: `harnessd --mcp [--mcp-workspace <dir>]` — starts an MCP stdio tool server instead of the HTTP API; ignores everything below.

Flags (`cmd/harnessd/main.go`):
| Flag | Default | Purpose |
|---|---|---|
| `--profile` | `""` | Named profile loaded from `~/.harness/profiles/<name>.toml` |
| `--mcp` | `false` | Start in MCP stdio mode instead of HTTP |
| `--mcp-workspace` | `.` (or `HARNESS_WORKSPACE`) | Workspace root for `--mcp` mode |

Signals (HTTP mode): `SIGINT`/`SIGTERM` shut down; `SIGHUP` triggers a live config reload (same mechanism as `POST /v1/config/reload`) instead of terminating.

Config layering (`internal/config/config.go`, lowest → highest precedence): `~/.harness/config.toml` → `.harness/config.toml` (workspace-relative) → named `--profile` TOML → `HARNESS_*` environment variables. Default listen address: **`:8080`** (`Addr` in `internal/config/config.go`).

**`POST /v1/runs/replay` response shapes:**
- `mode=simulate`, no drift detection: `{mode:"simulate", events_replayed int, step_count int, matched bool, mismatches []string}`.

- Errors: 400 `invalid_request` (missing `rollout_path` / bad mode / bad `fork_step`); 404 `rollout_not_found` (path escapes `HARNESS_ROLLOUT_DIR` containment, or tenant mismatch verified from the rollout's `run.started.tenant_id` field); 500 `replay_error`.

## 5. `harness.Event` envelope and SSE wire format

```go
type Event struct {
    ID        string         `json:"id"`         // "<runID>:<seq>" — parsed by harness.ParseEventID
    RunID     string         `json:"run_id"`
    Type      EventType      `json:"type"`
    Timestamp time.Time      `json:"timestamp"`
    Payload   map[string]any `json:"payload,omitempty"`
}
```

Wire format on `GET /v1/runs/{id}/events` (`writeSSE` in `internal/server/http.go`):
```
id: <runID>:<seq>
retry: 3000
event: <Type>
data: <json-encoded harness.Event>

```
A `: ping` comment line is written every `HARNESS_SSE_KEEPALIVE_SECONDS` (default 15s) of idle time. Resuming: send header `Last-Event-ID: <runID>:<seq>` to skip already-delivered history. Client reconnection is the caller's responsibility (the harnesscli TUI bridge — `cmd/harnesscli/tui/bridge.go` — implements bounded exponential-backoff reconnect, capped at 5 attempts, 200ms→3s backoff, treating 401/403/404 as non-retryable and everything else as retryable).

Terminal event types (stream closes after these — `harness.IsTerminalEvent`): `run.completed`, `run.failed`, `run.cancelled`.

|---|---|---|
| `workflow.started` | `Engine.Start`/`Resume` | `{workflow: string}`; on resume also `{resumed: true}` |
| `workflow.phase.started` | `Context.Phase()` | `{phase: string}` |
| `workflow.agent.started` | `Context.Agent()` | `{label, phase, prompt: string, isolation: string}` |
| `workflow.agent.completed` | `Context.Agent()` | `{label, phase: string, hasSchema: bool}` |
| `workflow.agent.failed` | `Context.Agent()` (start/poll/status/schema failures) | `{label, phase, error: string}`; sometimes `output` or `schemaError: true` |
| `workflow.log` | `Context.Log()` | `{message: string}` |
| `workflow.feedback` | `Context.Feedback()` (default kind) | `{kind, message: string, requires_response: bool, data: map[string]any (optional)}` |
| `workflow.finding` | `Context.Feedback(kind="finding", ...)` | same shape as feedback |
| `workflow.warning` | `Context.Feedback(kind="warning", ...)` | same shape as feedback |
| `workflow.question` | ask-question flow | question payload (kind/message/requires_response/data + call id) |
| `workflow.completed` (terminal) | end of `execute()` on success | `{workflow: string}` |
| `workflow.failed` (terminal) | end of `execute()` on script error | `{workflow, error: string}` |

The older step-based `internal/workflows` engine (`GET /v1/workflow-runs/{id}/events`) emits its own `workflows.Event{Seq, WorkflowRunID, Type string, Payload, Timestamp}` and is checked only against the literal strings `"workflow.completed"`/`"workflow.failed"` to close the stream — it does not share the `internal/workflow` `EventType` constants, so its full event-name catalog was not separately enumerated here.

## 8. Stateful IDs a native client must track

| ID | Minted by | Used in |
|---|---|---|
| `run_id` | `POST /v1/runs`, `.../continue`, `.../replay` (fork mode), `POST /v1/script-workflows/{name}/runs`, `POST /v1/subagents` | Every per-run route (`/v1/runs/{id}/...`), SSE stream URL, cancel/approve/deny/steer/compact/todos, `RunRequest.ConversationID` linkage |
| `conversation_id` | Client-supplied on first `POST /v1/runs` (or server-assigned if omitted — verify per-deployment), server-minted new ID on `POST .../fork` | All `/v1/conversations/{id}/...` routes; passed back into subsequent `POST /v1/runs` to keep a multi-turn session |
| `point_id` (rewind point) | Server, listed via `GET /v1/conversations/{id}/rewind-points` | `POST /v1/conversations/{id}/rewind` body |
| `checkpoint_id` | Server, emitted as part of a suspended tool/workflow state | `GET/POST /v1/checkpoints/{id}[/resume]`; linked to `run_id`/`workflow_run_id` inside the record |
| `call_id` | Server, on `tool.approval_required` / AskUserQuestion pause | Not directly addressed by a route (approval/deny/input act on the *run*, not the call, but the payload carries `call_id` for UI correlation) |
| Event `id` / seq (`"<runID>:<seq>"`) | Server, per SSE event | `Last-Event-ID` request header to resume a dropped stream without gaps or duplicates |
| `fork_from` / new `conversation_id` pair | `POST /v1/conversations/{id}/fork` response (`conversation_id`, `forked_from`) | Client bookkeeping for fork lineage |
| `workflow_run_id` (script or step workflow) | `POST .../runs` responses | `GET/POST /v1/{script-,}workflow-runs/{id}[/events` or `/resume]` |
| Subagent `id` | `POST /v1/subagents` | `GET/DELETE/wait/cancel /v1/subagents/{id}` |
| Cron `id` | `POST /v1/cron/jobs` | `GET/PATCH/DELETE/pause/resume /v1/cron/jobs/{id}` |
| API key (Bearer token) | Out-of-band (`store.CreateAPIKey`/`GenerateAPIKey`, not an HTTP route) | `Authorization` header on every request except webhook/trigger routes |
